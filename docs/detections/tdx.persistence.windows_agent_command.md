# `tdx.persistence.windows_agent_command`

This candidate detects Windows scheduled-task, autorun-key, and Startup-folder persistence requested through an agent tool call, in cmd tools and PowerShell cmdlets:

- scheduled tasks: `schtasks /Create`, and `Register-ScheduledTask` or `Set-ScheduledTask` with a `-TaskName`, `-Action`, `-Trigger`, `-Xml`, or `-InputObject` argument;
- autorun keys: `reg add`, `Set-ItemProperty`, or `New-ItemProperty` whose destination key is `Run`, `RunOnce`, `RunOnceEx`, or `Policies\Explorer\Run` under `Software\Microsoft\Windows\CurrentVersion`, or `Winlogon` under `Windows NT\CurrentVersion`, in HKCU or HKLM, including the `HKCU:` drive and `Registry::` provider forms;
- the Startup folder: `copy`, `move`, `xcopy`, `robocopy`, `Copy-Item`, or `Move-Item` with a Startup folder as the destination, and `shell:startup` used as a copy destination or with `Shell.Application` `CopyHere` or `MoveHere`.

It evaluates the Rule v1 `command` and `arguments` fields. Those fields prove that the agent requested the command; they do not prove that Windows accepted it or that persistence remains installed. Services, PowerShell profiles, and WMI subscriptions have their own rules in this pack: `tdx.persistence.windows_service_change`, `tdx.persistence.powershell_profile_write`, and `tdx.persistence.wmi_event_subscription`.

The bundled regex rule `persistence.shell_profile` covers Unix shell profiles, cron, `systemctl enable`, and `launchctl load`. The process-chain pack has Windows rules including `procchain.persistence.cmd_schtasks`, `procchain.persistence.powershell_schtasks`, and `procchain.persistence.reg_run_key`. Its adapter can derive process relationships from command text, so absence of observed parent-process telemetry does not by itself establish additional coverage.

At the pinned revisions, both Codex `compatible` and OpenCode `upstream` record `detected` with this rule matched and nothing missing for the `schtasks /Create`, Run-key, quoted Run and Winlogon key, Startup copy and quoted Startup copy scenarios, and for `detection.windows_powershell_run_key` (`Set-ItemProperty` on Run), `detection.windows_register_scheduled_task`, and `detection.windows_startup_shell_namespace` (`Shell.Application` `CopyHere` into `shell:startup`). Both formats record `clean` for the scheduled-task query, Run-key data reference, suffix-name, and Startup backup confounders, and for `detection.windows_persistence_read_only_audit` (`reg query`, `Get-ItemProperty`, `Get-ScheduledTask`, `sc query`, `Get-Service`, a WMI filter query, `Get-Content $PROFILE`, a Startup listing, and `explorer shell:startup`) and `detection.windows_persistence_docs_search` (a documentation search and `Get-Help` naming the cmdlets). `detection.windows_persistence_narrated_only` records `not_evaluable` / `labeled_not_evaluable`. These synthetic checks do not demonstrate Windows execution or real-world precision, and do not establish coverage for every included command form.

Expected false positives include authorized endpoint administration, approved scheduled-task installation, and requested startup configuration. The command alone cannot determine user authorization or final machine state.

The registry branch requires an autorun key as the destination: the key must follow `reg add` directly, or be the first `Set-ItemProperty` / `New-ItemProperty` argument or its `-Path` / `-LiteralPath` value, so `CurrentVersion\Run` in an unrelated value's data does not match. It accepts quoted keys, including quotes escaped in Codex's command array, and requires the key to end at an argument terminator. Backup keys such as Run-Backup are not autorun destinations. Reads and removals (`reg query`, `Get-ItemProperty`, `Remove-ItemProperty`) do not match.

The scheduled-task cmdlets need a task argument, so `Get-Help Register-ScheduledTask`, a documentation search that names the cmdlet, `Get-ScheduledTask`, and `Unregister-ScheduledTask` do not match. `Set-ScheduledTask` with a task name matches whatever it changes.

The copy-style branch uses two bounded positional arguments, with raw or serialized single or double quotes around either path. `Copy-Item` and `Move-Item` may name them with `-Path` and `-Destination`, in that order. Unquoted source tokens cannot contain quotes or begin with a slash or dash; this prevents a quoted source from being split at Start Menu, and a leading switch or parameter name from becoming the source during regex backtracking. Up to two `/Y` or `/-Y` switches may precede the source. Startup must be a complete destination component, followed by a path separator or the end of the argument, not a prefix such as Startup-old. The source and each destination-path segment around Startup have a 240-character matching bound, measured in the searchable representation, so JSON escaping can exhaust a bound sooner. Opening the folder with `explorer shell:startup` does not match. This is not a complete Windows command-line parser: other switches, other parameter orders, indirect scripts, a quoted path that contains the other quote character, and longer paths can be missed.

An arbitrary directory actually named Startup may still match even when it is not the Windows logon Startup folder. Quoted command examples with their arguments can also match because the rule searches command text rather than parsing shell execution. The Winlogon branch does not distinguish execution-related values from ordinary settings under that key. Not covered: the `Wow6432Node` and `RunServices` keys, `New-Item` under an autorun key, persistence through APIs, GUI tools, scripts whose relevant content is absent from searchable arguments, and commands outside the included forms. Severity high, score 55, and test maturity are unchanged.
