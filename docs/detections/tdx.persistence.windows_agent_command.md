# `tdx.persistence.windows_agent_command`

This candidate detects Windows persistence commands requested through an agent tool call: `schtasks /Create`, `reg add` against common autorun keys, and copy-style commands targeting a Startup folder. It evaluates the Rule v1 `command` and `arguments` fields. Those fields prove that the agent requested the command; they do not prove that Windows accepted it or that persistence remains installed.

The bundled regex rule `persistence.shell_profile` covers Unix shell profiles, cron, `systemctl enable`, and `launchctl load`. The process-chain pack has Windows rules including `procchain.persistence.cmd_schtasks`, `procchain.persistence.powershell_schtasks`, and `procchain.persistence.reg_run_key`. Its adapter can derive process relationships from command text, so absence of observed parent-process telemetry does not by itself establish additional coverage. In the synthetic scheduled-task case at Telltale `2e8c56a`, the bundled `procchain.persistence.cmd_schtasks` rule matched OpenCode while no bundled persistence rule matched Codex. This candidate matched both, adding coverage for the tested Codex argument representation and overlapping the bundled OpenCode signal. This evidence does not establish additional coverage for every included Windows command form.

Expected false positives include authorized endpoint administration, approved scheduled-task installation, and requested startup configuration. The command alone cannot determine user authorization or final machine state. It also misses Windows persistence performed through APIs, GUI tools, scripts whose relevant content is not present in searchable arguments, or commands outside the included scheduled-task, autorun-key, and Startup-folder forms.
