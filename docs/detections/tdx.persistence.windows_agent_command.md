# `tdx.persistence.windows_agent_command`

This candidate detects Windows persistence commands requested through an agent tool call: `schtasks /Create`, `reg add` against common autorun keys, and copy-style commands targeting a Startup folder. It evaluates the Rule v1 `command` and `arguments` fields. Those fields prove that the agent requested the command; they do not prove that Windows accepted it or that persistence remains installed.

The bundled regex rule `persistence.shell_profile` covers Unix shell profiles, cron, `systemctl enable`, and `launchctl load`. The process-chain pack has Windows rules including `procchain.persistence.cmd_schtasks`, `procchain.persistence.powershell_schtasks`, and `procchain.persistence.reg_run_key`. Its adapter can derive process relationships from command text, so absence of observed parent-process telemetry does not by itself establish additional coverage. At the pinned revisions, both Codex `compatible` and OpenCode `upstream` record `detected` for `detection.windows_scheduled_task_create` (matched: `tdx.persistence.windows_agent_command`; missing: none), `clean` for `detection.windows_scheduled_task_query` (matched and missing: none), and `not_evaluable` / `labeled_not_evaluable` for `detection.windows_persistence_narrated_only` (matched and missing: none). A Codex `compatible` comparison, if retained, is that profile only. This evidence does not establish additional coverage for every included Windows command form.

Expected false positives include authorized endpoint administration, approved scheduled-task installation, and requested startup configuration. The command alone cannot determine user authorization or final machine state. The `reg add` branch requires a Windows autorun key as the destination, rather than matching `CurrentVersion\\Run` in an unrelated value's data. It accepts quoted keys, including quotes escaped in Codex's command array, and requires the Run, RunOnce, or Winlogon key to end at an argument terminator. Backup keys such as Run-Backup are not autorun destinations.

The copy-style branch uses two bounded positional arguments, with raw or serialized double quotes around either path. Unquoted source tokens cannot contain quotes or begin with a slash; this prevents a quoted source from being split at Start Menu or a leading switch from becoming the source during regex backtracking. Up to two `/Y` or `/-Y` switches may precede the source. Startup must be a complete destination component, followed by a path separator or the end of the argument, not a prefix such as Startup-old. The source and each destination-path segment around Startup have a 240-character matching bound, measured in the searchable representation, so JSON escaping can exhaust a bound sooner. This is not a complete Windows command-line parser: other switches, indirect scripts, unusual quoting, and longer paths can be missed.

The pinned and supplemental current-source assessments detect the quoted Run and Winlogon keys and the quoted Startup copy with `/Y` in both formats. Both keep the realistic quoted Startup backup and suffix-name confounders clean. The earlier unquoted-source cases remain covered; these synthetic checks do not demonstrate Windows execution or real-world precision.

An arbitrary directory actually named Startup may still match even when it is not the Windows logon Startup folder. Quoted command examples can also match because the rule searches command text rather than parsing shell execution. The Winlogon branch does not distinguish execution-related values from ordinary settings under that key. Windows persistence through APIs, GUI tools, scripts whose relevant content is absent from searchable arguments, or commands outside the included forms remains uncovered. Severity high, score 55, and test maturity are unchanged.
